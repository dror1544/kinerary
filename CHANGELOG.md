# Changelog

## How this file works

- Newest sprint on top. Inside a sprint, newest entry first (by merge date; ties by PR number, highest first). There are no version tags: the sprint is the version unit.
- Every entry says what changed and for whom, and why it matters. New features lead with the value; fixes lead with the problem. References follow on one line: issue (`#n`), PR (`PR #n`), or a short commit hash only when neither exists.
- Each sprint is an H2 with a bold status line. A closed sprint gets a CLOSED status line (date and merge commit) and a boundary marker at the bottom of its section, so an entry from a different sprint is visibly across a line.
- To open the next sprint: add a new `## Sprint N` section ABOVE the previous one, separated by `---`, and change the previous sprint's status line to CLOSED.

## Sprint 6 — Verification, explicit activation, dashboard, and demo rehearsal (2026-09-20 → open)

**OPEN — unreleased. On integration/sprint-6; not yet on main, not deployed.**
Baseline: `97582b6`. Release: none yet. Scope and track breakdown: `docs/sprint6-tracks.md`.

### New

- **A trip now opens as the trip site itself, not inside a frame in the dashboard, and an organizer can get back to the dashboard from the trip's menu.** The dashboard (and the Telegram Mini App) wrapped every trip in a frame under a "← Trip setup" bar. That frame cost screen space, blanked trip documents (a PDF opened from the frame showed an empty page) and made the page behave unlike the installed app. Now "Open trip" hands the one-time launch grant to the trip's address with an ordinary form submission (the grant is in the request body, never in a web address), the trip site takes over the whole screen, and there is no second sign-in. Owners and organizers see **Organizer dashboard / לוח המארגן** in the trip's side menu (Modern and Classic) that leads back; members never do. Behind it: the gateway accepts a launch only from the dashboard's own address (a launch from any other page, or with no origin, is refused), keeps one cookie per trip that is set for same-site use only, and on every request checks (at most every 30 seconds) that the person is still signed in to the dashboard and still on the trip — signing out of the dashboard, or being removed, ends the trip session. A trip page opened without a session sends the browser to the dashboard to sign in and come back; the old wait-for-a-message page is gone. Trips opened this way share one address, so their sign-in markers in the browser are now kept per trip, and the dashboard link is held in memory only. Going "back" from the trip never re-submits a spent grant: the dashboard shows "Open trip again" instead. In Telegram's browser clients (which run the Mini App in a frame) the Mini App offers "Open trip in a new tab". Known limits: connecting Claude or ChatGPT from a trip opened this way still asks for one sign-in on the trip's own address; the dashboard and the trip address must be on the same site (the cookie is Strict) or the launcher stops after three tries with a message; the session check treats "signed in" as any live dashboard session of that person (binding to the exact one needs a database column and is proposed separately); opening documents inside Telegram's own browser (#417, Telegram half) is a follow-up. **Not merged and not deployed. The dashboard and gateway parts reach people when the control plane is next restarted; the trip's menu entry, the dashboard link and the per-trip sign-in markers reach a trip only when that trip is redeployed with a release built after this change, and until then its menu simply has no dashboard entry. Trip tabs signed in before the restart must be opened again from the dashboard (the cookie has a new name).** #431, #440.
- **A trip's stops can now be changed after the interview: set a stop's dates and hotel from a hotel booking, split a stay in two, move a day to another stop.** Until now the stops the interview produced were fixed. A companion could record the family's hotel booking and say "added" while the Journey tab did not move, and nothing on the site or in chat could change a stop's dates, split it or move a day between stops (found in a manual test on 2026-10-10). Now an organizer can do all three by chat with the companion, or in the Modern site's plan tools (a Stops editor with history and restore, and a "move this day to…" control). The link between a booking and its stop is explicit: nothing guesses which stop a hotel belongs to, and a booking filed under another stop, or already linked to one, is refused rather than moved. Setting a stop from a hotel booking gives it the booking's nights and the hotel's name, confirmation and map link (never the door code or the booking notes) and puts one check-in and one check-out on the plan, once, however many times it is repeated. A change that would leave plan items outside a stop's new dates is refused with the list, and the organizer chooses to keep them or move them; dates outside the trip's own dates are refused. The "N days not assigned to a stop" notice is now computed from the stops and the plan, so it clears when the days are covered (before, its count was written once when the trip was built). Edits live in the trip site's own database and are laid over the built trip, so a rebuild does not lose them; if a rebuild changes something an organizer had already changed, theirs is kept and the editor flags the difference. Every change is recorded with who made it and can be undone. Only an organizer, or the companion acting for one, can make or see them, and the public site serves exactly the fields it served before. A `"` in stop text is kept as typed, so Hebrew abbreviations such as ארה"ב work. Known gaps: edits change the trip site only and are not written back to the interview's record; restoring the saved plan does not restore stops (a stop has its own undo); a conflict after a rebuild is resolved for a whole stop, not field by field; follow-ups are tracked in #365 and #369. Benefits organizers; the family see the right dates and hotel. **Not merged and not deployed. The site part (and the rebuilt Modern site bundle) reaches a trip only when that trip is redeployed; until then nothing changes for any trip.** PR #362.
- **The companion can now change stops, and is told to link a hotel booking to its stop.** Five tools on the companion's bridge and on the site's own connector (`get_stops`, `update_stop`, `split_stop`, `set_stop_from_booking`, `move_plan_day`), with the instructions to use them: a hotel booking is linked to its stop (adding the booking alone changes no stop), the stops are read back before anything is called done, and only the organizer, in their private chat, asks for these changes. Benefits organizers. **Not merged and not deployed. The tools reach a trip's companion only after that trip's bridge is refreshed, and the instructions only after its companion profile is refreshed (a family group's open conversation keeps its saved prompt until that is cleared). The companion has not yet been run against a live model on these instructions.** PR #362.
- **A new end-to-end scenario, `star`, replays the shape of a real manual test with made-up people:** a couples trip that sleeps in one town and day-trips from it, flying through a gateway city, followed by a hotel booking and a change of stops told to the companion, all judged on the built site rather than the chat. It is not part of `--scenario all` or the nightly run, and has not yet been run live. Benefits the team. PR #361.
- **The daily control-plan report now shows real numbers for whether the assistant could actually answer from trip data**, instead of a hardcoded "no data recorded": a grounded-answer rate, a missing-data rate, and the top 3 things most often missing that an organizer could add. Benefits the team. Scope was narrowed for this sprint (`docs/sprint6-tracks.md` decision 22): turning a missing fact into an actual request to the organizer, and tracking whether they filled it, move to next sprint — this slice only detects and reports. Still off by default everywhere (`ASSISTANT_EVENTS_ENABLED` unset, not switched on in any deployment). #177, PR #351.
- **An operator can now suspend a trip or retry a failed build from the admin dashboard, instead of by hand on the server.** Suspending and resuming both require a real reason, and every suspend, resume and retry is recorded on its own audited row through the same operator key the read-only dashboard already used. A trip's suspension history is kept as a durable record of its own, so resuming a trip never erases why it was paused. Operator-only; completes the two-slice dashboard build (the read-only half shipped earlier as PR #275). Boundary-reviewed before merge: a race between claiming a job and suspending it, audit-log pollution from a malformed trip id, a Unicode control-character gap in the reason field, and an unaudited refusal path were all found and fixed. PR #348.

It ships off by default and is not switched on in any deployment, and richer outcomes this build list also calls for (a distinct "missing information" result, an organizer follow-up, a post-write check) are not part of this slice. #177, PR #347.

Votes survive a re-provision. Benefits travellers and organizers. #169, PR #171. (Classic site's RSVP section still cannot render; tracked in #170 — addressed by PR #363, see Fixed.)
- **Each phase of a new trip can get a season-appropriate packing list, and only when the place and the season are known.** A short bilingual list, chosen from the phase's named city and every month the phase covers, with no network or model call. A phase that names no city the system knows, or a place with no clear winter and summer (tropical, desert, Mediterranean, monsoon), or a phase that spans seasons, gets no list, and the site shows its generic one. - **A trip site could serve a configuration field nobody chose to show.** The site removed a list of known-private fields from a trip's configuration before serving it, so any field nobody had thought to list reached every signed-in family member. It now serves only fields on an explicit list of what the site and the assistant need, and drops the rest (with a count of dropped fields). Benefits every family on a trip; security fix. **Nothing changes for anyone yet:** new trips get it once a release carrying it is promoted, and each existing trip keeps its current site until it is redeployed by hand. Redeploying an existing trip can hide fields it shows today (the audit found 40 fields of 12 kinds on the USA trip's local configuration, for example), so each redeploy is a decision; tracked, with some small defects the audit found, in #200. Closes #172, PR #196.
- **Packing lists could be wrong for the place and the season.** The first version of the per-phase packing list guessed a hemisphere from the trip's destination and defaulted to north, so a city-only destination such as Sydney, a multi-country trip, or a Hebrew spelling with a geresh could get winter items in summer, and a tropical or desert stop could get a "warm jacket" list. A phase now gets a list only when its named city is known to have a real winter and summer and every month it covers is clearly one season; otherwise it gets none and the site shows its generic list. This only ever removes packing output; nothing is added. The UK stays temperate, with the Isles of Scilly excepted. Benefits travellers. Nothing changes for anyone until a release carrying it is promoted and a trip is built or rebuilt on it. Known gaps, tracked in #201: the climate table's borderline months are not yet checked against a published source, and no coverage on real destinations has been measured. Closes #167, PR #197.
- **A failed attempt to connect an assistant to its trip was being erased, so nobody could see it.** When a new trip's assistant could not be wired to the trip's data, the failure was recorded, and then a chat successfully binding to the trip overwrote it with "reachable". The operator's monitoring never saw an assistant that could not read its own trip. The record of the failure is now kept. This is not a fix for the underlying problem: #119 stays open because the root cause is not established, and trips already running are not helped by this change. A repair-path regression to sort out before the sprint's release reaches the VM is tracked in #193. Benefits the operator. Addresses #119 (still open), PR #182.
- **A torn-down trip could still be attached to a chat.** After teardown, a chat (or a group binding link valid for 7–30 days) could be bound to the retired trip, leaving a companion that could never connect: the operator's release verify stayed red and every relay restart waited 40 seconds for it. All five places that could do this now refuse a retired trip (the group link, the operator invitation, the wait for a new trip's assistant, the trip list, and the `/switch` command), and teardown revokes still-live group links (ordering chosen to avoid a database deadlock). One narrow timing race remains: a chat can still end up bound to a trip that is torn down in the same instant as the check. It is left unlocked on purpose, because a lock caused the deadlock above, and it is documented in the code; recovery is to `/switch` to another trip or re-run teardown. Benefits the operator. #105 and #175 are closed on GitHub (by hand, with evidence comments); the fix is on the sprint branch only. PR #174, PR #176, PR #180.
- **Documents with no type or name from Telegram were refused.** A PDF sent as a phone "share/save as PDF" arrived typeless (as `.bin`) and was rejected on a live trip. The file type is now recognised from the file's own bytes (PDF, JPEG, PNG, GIF). Files with a genuinely malformed PDF trailer still fail; that is separate. Benefits travellers. #163 (still open), PR #166.
- **A chat could be bound to a trip on an unverified hint.** Bindings and companion introductions now come only from a verified Telegram identity or the chat the interview ran in; without one the bind is refused and the reason recorded. The unverified id may still be used to send a notification, never to route or authorize. Security fix. #32 is closed on GitHub (by hand, 2026-09-25); the fix is on the sprint branch only. PR #149.
- **Operator: model calls for the interview ran with more of the machine's environment than needed.** The Claude CLI path now passes an allowlisted set of variables, and the Codex path is isolated from shell, web and tool access and from relay secrets. Reduces what a crafted document could reach. PR #91, PR #144; completed for the Claude and Hermes paths and the Codex check by PR #192 (see above).
- **Teardown adopted an IP pool it never uses.** A pool set in the environment could be picked up by teardown, colliding with a range the live control plane reserves. Teardown now carries none. Benefits the operator. PR #108.
- **Ticketed events, shuttles and parking were filed as "other".** A booked event, shuttle or parking stopped reading as a booking on the site. They are now treated as bookings, matching a fix already on main. Benefits organizers and travellers. PR #143.
- **Journey, Today and weather views disagreed with the trip's dates.** During a trip Journey now opens on the current day and phase; Today no longer shows a past activity when nothing is upcoming; weather follows the trip from the first destination through later phases. Benefits travellers. Already on main. PR #152 (merged to main; carried here as `59ed025`).
