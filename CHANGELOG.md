# Changelog

## How this file works

- Newest sprint on top. Inside a sprint, newest entry first (by merge date; ties by PR number, highest first). There are no version tags: the sprint is the version unit.
- Every entry says what changed and for whom, and why it matters. New features lead with the value; fixes lead with the problem. References follow on one line: issue (`#n`), PR (`PR #n`), or a short commit hash only when neither exists.
- Each sprint is an H2 with a bold status line. A closed sprint gets a CLOSED status line (date and merge commit) and a boundary marker at the bottom of its section, so an entry from a different sprint is visibly across a line.
- To open the next sprint: add a new `## Sprint N` section ABOVE the previous one, separated by `---`, and change the previous sprint's status line to CLOSED.

## Sprint 7 — Hardening, safe upgrades, one origin (2026-10-19 → open)

**OPEN — unreleased, on main.**
Baseline: `03c0e1c`. Release: none yet. Scope and track breakdown: `docs/onboarding-mvp-sprint-plan.md#sprint-7--hardening-safe-upgrades-one-origin`.

### New

- **A trip now opens as the trip site itself, not inside a frame in the dashboard, and an organizer can get back to the dashboard from the trip's menu.** The dashboard (and the Telegram Mini App) wrapped every trip in a frame under a "← Trip setup" bar. That frame cost screen space, blanked trip documents (a PDF opened from the frame showed an empty page) and made the page behave unlike the installed app. Now "Open trip" hands the one-time launch grant to the trip's address with an ordinary form submission (the grant is in the request body, never in a web address), the trip site takes over the whole screen, and there is no second sign-in. Owners and organizers see **Organizer dashboard / לוח המארגן** in the trip's side menu (Modern and Classic) that leads back; members never do. Behind it: the gateway accepts a launch only from the dashboard's own address (a launch from any other page, or with no origin, is refused), keeps one cookie per trip that is set for same-site use only, and on every request checks (at most every 30 seconds) that the person is still signed in to the dashboard and still on the trip — signing out of the dashboard on one device ends the trip session opened from that device (the one opened from another device keeps working), and being removed from the trip ends them all; a change of someone's role at the control plane (for example an organizer demoted to member) ends the session opened with the old role too, so they open the trip again and no longer see the organizer menu entry. The trip only accepts a dashboard link that points at the dashboard's own address, and a hung control plane makes the gateway refuse quickly instead of waiting. A trip page opened without a session sends the browser to the dashboard to sign in and come back; the old wait-for-a-message page is gone. Trips opened this way share one address, so their sign-in markers in the browser are now kept per trip, and the dashboard link is held in memory only. Going "back" from the trip never re-submits a spent grant: the dashboard shows "Open trip again" instead. In Telegram's browser clients (which run the Mini App in a frame) the Mini App offers "Open trip in a new tab". Known limits: connecting Claude or ChatGPT from a trip opened this way still asks for one sign-in on the trip's own address; the dashboard and the trip address must be on the same site (the cookie is Strict), and the gateway refuses to start, with a clear error, when they are not; opening documents inside Telegram's own browser (#417, Telegram half) is a follow-up. **Not merged and not deployed. Adds one nullable column (migration 20261020130000, rollback compatible) to the launch grants. The dashboard and gateway parts reach people when the control plane is next restarted; the trip's menu entry, the dashboard link and the per-trip sign-in markers reach a trip only when that trip is redeployed with a release built after this change, and until then its menu simply has no dashboard entry. Trip tabs signed in before the restart must be opened again from the dashboard (the cookie has a new name).** #431, #440.

## Sprint 6 — Verification, explicit activation, dashboard, and demo rehearsal (2026-09-20 → 2026-10-19)

**CLOSED 2026-10-19 — on main since PR #356 (2026-10-18); last merge `03c0e1c`.**
Baseline: `97582b6`. Release: none recorded in this file. Scope and track breakdown: `docs/sprint6-tracks.md`. At close, entries that said "not merged" or "on the sprint branch" were corrected to say they are on main; each entry's own note on what has to be redeployed or refreshed before a trip sees it still stands, and this file does not record which trips run what.

### New

- **An operator can now clear the interview and intake data of a trip that was never built, and the clear is previewed and archived first.** Until now there was no production way to reset a trip that had not been provisioned: the two scripts closest to it refuse on purpose. Two operator-key routes (a preview, then the clear) now remove the trip's interview and intake data, keeping an archive of what was removed. The clear refuses, with no override, any trip that shows a sign of ever having been built: a job claimed, a chat or group link that ever existed, or a lifecycle state of provisioning or beyond. Operator-only, and unmounted unless the operator key is configured (see the fix for the VM below). Known gap: clearing a trip that was built is not covered and is tracked in #390; there is no route to restore an archive. #378 (closed on GitHub), PR #410.
- **A group can now decide whether the assistant also joins in when nobody addressed it, and an unaddressed group message can be judged for whether it was meant for the assistant.** `/proactive 1|2|3` sets a group's level: 1 only when called, 2 also follows the conversation, 3 also asks the judge (default 3). The judge is a small model that sees an unaddressed message, and when it fails or is unsure the message counts as not addressed; its hits and misses are recorded and counted in the daily report. **It ships off unless a judge model is configured, and none is configured anywhere: no model has been checked live, the targets (precision at least 90%, recall at least 75%, answer within 1.5 seconds) have not been measured, and the VM's compose file does not yet pass the judge settings to the relay.** The group introduction does not mention it, and the Hebrew copy needs the owner's read. Benefits families in groups. PR #407.
- **In a Telegram group, the assistant now keeps talking with the person it is talking with, without needing its name each time, for five minutes.** In a manual test on 2026-10-16, 6 of 9 untagged follow-ups were dropped, because the only window that existed opened when the assistant ended with a question. Now once the assistant is talking with a member, that member's own follow-ups reach it, each exchange renews the window, and everyone else still has to address it by name, mention, reply or the question window. A trip's existing opt-out switches the window off too. Known gaps: a reply that takes longer than five minutes closes the window before it arrives; untagged photos and files from that member are forwarded too; the member who answers a question becomes the partner. Benefits families in groups. **Reaches a trip through a release carrying it (an additive, rollback-compatible database migration) and a relay restart.** PR #406 (with an end-to-end test of the window, PR #408).
- **One link now joins the assistant to a group.** The organizer taps a link in the introduction, picks a group and allows pinning; the group is bound without copying a `/group KIN-…` line by hand (that line still works and is still sent). The link uses the same checks as `/group` (sender, expiry, retired trip, already bound elsewhere), and the bot's handle is looked up from Telegram when none is configured, which is why no link appeared in a staging greeting before. Benefits organizers. **Not verified in a real Telegram group:** that Telegram posts the start message from the adding user, the admin and pin dialog, and the order of join events; a "no trip for this chat yet" reply may flash just before binding. The new copy needs the owner's read. PR #402.
- **New trips now get the "connect ChatGPT or Claude" connector switched on.** The connector existed (PR #228) but a new trip never got it, with no warning, because the two settings it needs were written by hand for the one trip that had it. A trip built after the worker runs a release carrying this gets both settings. Existing trips are unchanged; connecting still needs a site password or Google sign-in. Benefits families and organizers. PR #396.
- **A typed trip type that fits no option is now kept and flagged for the assistant to settle with the organizer.** The trip type never blocks building the trip, but it shapes later planning (pace, who suggestions are for), so free text must not look settled. The organizer's words are kept verbatim in an organizer-only standing instruction telling the assistant that the type is not settled and to settle it early. The marker is never served to the site. Known gap: the assistant has no tool to write the settled type back, so it lives only in its memory; that needs an owner decision. Benefits organizers. PR #392.

- **A trip's stops can now be changed after the interview: set a stop's dates and hotel from a hotel booking, split a stay in two, move a day to another stop.** Until now the stops the interview produced were fixed. A companion could record the family's hotel booking and say "added" while the Journey tab did not move, and nothing on the site or in chat could change a stop's dates, split it or move a day between stops (found in a manual test on 2026-10-10). Now an organizer can do all three by chat with the companion, or in the Modern site's plan tools (a Stops editor with history and restore, and a "move this day to…" control). The link between a booking and its stop is explicit: nothing guesses which stop a hotel belongs to, and a booking filed under another stop, or already linked to one, is refused rather than moved. Setting a stop from a hotel booking gives it the booking's nights and the hotel's name, confirmation and map link (never the door code or the booking notes) and puts one check-in and one check-out on the plan, once, however many times it is repeated. A change that would leave plan items outside a stop's new dates is refused with the list, and the organizer chooses to keep them or move them; dates outside the trip's own dates are refused. The "N days not assigned to a stop" notice is now computed from the stops and the plan, so it clears when the days are covered (before, its count was written once when the trip was built). Edits live in the trip site's own database and are laid over the built trip, so a rebuild does not lose them; if a rebuild changes something an organizer had already changed, theirs is kept and the editor flags the difference. Every change is recorded with who made it and can be undone. Only an organizer, or the companion acting for one, can make or see them, and the public site serves exactly the fields it served before. A `"` in stop text is kept as typed, so Hebrew abbreviations such as ארה"ב work. Known gaps: edits change the trip site only and are not written back to the interview's record; restoring the saved plan does not restore stops (a stop has its own undo); a conflict after a rebuild is resolved for a whole stop, not field by field; follow-ups are tracked in #365 and #369. Benefits organizers; the family see the right dates and hotel. **On main (PR #356). The site part (and the rebuilt Modern site bundle) reaches a trip only when that trip is redeployed; until then nothing changes for any trip.** PR #362.
- **The companion can now change stops, and is told to link a hotel booking to its stop.** Five tools on the companion's bridge and on the site's own connector (`get_stops`, `update_stop`, `split_stop`, `set_stop_from_booking`, `move_plan_day`), with the instructions to use them: a hotel booking is linked to its stop (adding the booking alone changes no stop), the stops are read back before anything is called done, and only the organizer, in their private chat, asks for these changes. Benefits organizers. **On main (PR #356). The tools reach a trip's companion only after that trip's bridge is refreshed, and the instructions only after its companion profile is refreshed (a family group's open conversation keeps its saved prompt until that is cleared). The companion has not yet been run against a live model on these instructions.** PR #362.
- **A new end-to-end scenario, `star`, replays the shape of a real manual test with made-up people:** a couples trip that sleeps in one town and day-trips from it, flying through a gateway city, followed by a hotel booking and a change of stops told to the companion, all judged on the built site rather than the chat. It is not part of `--scenario all` or the nightly run, and has not yet been run live. Benefits the team. PR #361.
- **The daily control-plan report now shows real numbers for whether the assistant could actually answer from trip data**, instead of a hardcoded "no data recorded": a grounded-answer rate, a missing-data rate, and the top 3 things most often missing that an organizer could add. Benefits the team. Scope was narrowed for this sprint (`docs/sprint6-tracks.md` decision 22): turning a missing fact into an actual request to the organizer, and tracking whether they filled it, move to next sprint — this slice only detects and reports. Still off by default everywhere (`ASSISTANT_EVENTS_ENABLED` unset, not switched on in any deployment). #177, PR #351.
- **An operator can now suspend a trip or retry a failed build from the admin dashboard, instead of by hand on the server.** Suspending and resuming both require a real reason, and every suspend, resume and retry is recorded on its own audited row through the same operator key the read-only dashboard already used. A trip's suspension history is kept as a durable record of its own, so resuming a trip never erases why it was paused. Operator-only; completes the two-slice dashboard build (the read-only half shipped earlier as PR #275). Boundary-reviewed before merge: a race between claiming a job and suspending it, audit-log pollution from a malformed trip id, a Unicode control-character gap in the reason field, and an unaudited refusal path were all found and fixed. PR #348.
- **The team's usage-event record (see PR #181 below) can now also capture what the assistant's own tools told it** — a grounded answer backed by real trip data, or a tool call that found nothing to answer with — through a new collector running inside Hermes and a new, authenticated route into the control plane. This is the half PR #181 said was still missing; nothing changes for any family yet. It ships off by default and is not switched on in any deployment, and richer outcomes this build list also calls for (a distinct "missing information" result, an organizer follow-up, a post-write check) are not part of this slice. #177, PR #347.
- **A family member can connect their own Claude or ChatGPT to their trip site, with their normal site login.** They ask the assistant about the trip and see what the site would show them, never more; organizers can also make changes, everyone else is read-only. It is off by default and switched on per trip. It has been live on one real trip since 2026-09-25 from `main`; this carried it into this sprint's code, byte-for-byte, so a trip built from a release carrying this sprint will have it available. Not deployed by this change: turning it on for more trips needs the owner's approval, and boundary-review findings and two small gaps (a tool without a test, stale comments) are still open. #227, PR #228 (built as PRs #219 and #220 on `main`).
- **The team can now see how the assistant is being used in a trip's chats without reading a single message.** A new event record notes, for each trip, that a group message was or was not addressed to the assistant, that a request was handed to it, that a reply went out and whether Telegram accepted it, that a turn was lost because nothing could take it, and how the assistant's document reading ended. It holds no message text, no names, no chat or user identifiers and no file names, and the database refuses anything else. It never records a turn as "answered", because it sees delivery, not what the assistant did. Benefits the team, and later the organizer report. **Ships off and is not switched on anywhere**: it records nothing until an operator turns it on. Not built yet at the time: the assistant-side collector, the intake route, the rates, the daily report, the dashboard, and scheduled deletion (the 90-day purge exists but is not scheduled). **The assistant-side collector and the intake route are now built — see above, PR #347.** The owner confirmed on #177 (2026-09-25) that this metadata-only approach is right for the family-and-friends MVP; a notice to families is deferred to full production (#186). One part was inert: a document-correction record the relay builds was never used until PR #215 connected the route that produces it (#178; see Fixed). #177, PR #181.
- **Activities the family can vote on now appear on a new trip.** A trip built from an interview lists its not-yet-booked attractions on the "Activities and places" tab as votable items; attractions already booked stay on Bookings only. Votes survive a re-provision. Benefits travellers and organizers. #169, PR #171. (Classic site's RSVP section still cannot render; tracked in #170 — addressed by PR #363, see Fixed.)
- **Each phase of a new trip can get a season-appropriate packing list, and only when the place and the season are known.** A short bilingual list, chosen from the phase's named city and every month the phase covers, with no network or model call. A phase that names no city the system knows, or a place with no clear winter and summer (tropical, desert, Mediterranean, monsoon), or a phase that spans seasons, gets no list, and the site shows its generic one. Benefits travellers. #162, PR #165; reworked to abstain by PR #197 (see Fixed). The first version chose a hemisphere from the trip's destination and defaulted north.

Only that one question allows it, because the other answers must be bilingual on the site. The multi-select "Done" half of #42 is not built. Addresses #42 (partly; still open), PR #150.

Existing trips do not change until re-provisioned. Known gap: a destination only gets data if the interview looked up that country (#159). #156, PR #160.

### Fixed

- **A new trip site's first login worked on every other trip too, and the VM never received the operator and admin keys.** Two problems, two PRs. The VM's compose file passed neither `CONTROL_PLANE_OPERATOR_KEY` nor `CONTROL_PLANE_ADMIN_KEY` to the control-plane API, so every operator route (invitations, the new trip clear) and every admin dashboard route answered 503 on the VM; both are now passed through, optional, so a VM without them still boots with those routes off (PR #411). Separately, one deployment-wide seed password gave every trip site the same first password, so a member of one trip could log in to the next as any participant (found 2026-10-15). Each new trip now generates its own 16-character password, kept in that site only and never rotated by a re-provision, and the organizer receives it in the private introduction; the shared setting is retired. Existing trips keep their old password. Benefits every family and the operator. Boundary review was requested on the password path (PR #398). PR #411, PR #398.
- **The assistant could answer silence to a message that named it, and answered an emoji as if it were a request.** Found in the owner's staging run of 2026-10-17. A message that names the assistant, mentions the bot or replies to it now reaches it marked as directly addressed, with the bot's own handle; if it still stays silent, the relay logs it and the daily report counts it as a defect. A message made only of emoji passes through the window or the judge only when it answers a question the assistant asked (a thumbs-up after "update the site?" counts, a laughing face after a statement does not), and a thank-you now gets a brief warm reply. Known gap: a live assistant keeps its old behaviour until its prompt is re-rendered and its group sessions are ended; a helper for that is a follow-up. Benefits families in groups. **Needs a database migration (compatible) and a relay restart.** PR #409.

A missing name is logged by count and does not block. The PR did not verify the live model. Re-provisioning an earlier intake changes its Hebrew-only logins. Benefits organizers. PR #400.

The Journey, Today, the map, "Tonight" and the Classic site show the same name, a Maps link and a Waze link; a booking's PIN and notes still do not appear in the config or the plan. The interview now notices flight numbers in typed messages, holds the summary until the flights are asked about once, and records nothing from the detection alone.
