Kinerary on k3s

Target architecture for moving Kinerary and a dedicated Hermes AI runtime from the current Mac/Compose-oriented deployment into a reproducible k3s platform on Proxmox, while preserving the product control-plane contracts and simplifying trip provisioning.

1. Architecture principles

  • Kinerary and Hermes are one product stack, not one process. Hermes is a critical application dependency, but remains an independently managed workload.
  • k3s is the only container orchestration layer in the VM. The baseline does not run a parallel Docker daemon for production workloads.
  • Trips are logical tenants, not public infrastructure endpoints. New trips are reached through a wildcard hostname under a dedicated Kinerary Cloudflare tunnel; they do not receive per-trip Cloudflare tunnel/DNS entries, NPM hosts, or public IPs, and browser-origin isolation between trips is preserved because each trip keeps its own hostname.
  • Control-plane contracts survive the migration. The provider-specific Proxmox/LXC provisioning implementation is replaced by a Kubernetes adapter; canonical plans, jobs, releases, approvals, and audit records remain.
  • Recoverability before high availability. The first production cluster is intentionally one k3s server on one Proxmox VM, created only after a documented Proxmox host-preparation pass frees the RAM and CPU headroom it needs. Backups, immutable images, and reproducible manifests are higher priority than multi-server Kubernetes.
  • Local databases; NAS for blobs and backups, with an off-host copy. PostgreSQL and SQLite write paths stay on local block storage. TrueNAS NFS is used for document-like content and as the primary backup target; Google Drive holds an off-host copy of the database-class backups, and may optionally be attached per user as a document source alongside NFS.

  • extract/enrichment profiles

Trip tenancy

A trip remains a tenant with its own application state and lifecycle, but the companion does not receive a separate Kubernetes data volume by default. Companion configuration is derived from the trip's canonical data/profile bundle and runs in the Hermes plane. Any durable Hermes conversation/workspace state belongs to the Hermes persistence model, keyed by trip/profile identity, rather than to a second per-trip storage silo.

Clarification of “companion-specific state”: there is no proposed standalone companion-data PVC. If Hermes later proves that a profile must have isolated durable filesystem state, that isolation can be introduced explicitly. Until then, per-trip durable data belongs either to the trip runtime/database or to the shared Hermes state store with tenant-scoped directories/records.

Trip runtime representation

Implementation may use a namespace per trip or a shared kinerary-trips namespace with strict labels and NetworkPolicies. The initial recommendation is a shared trips namespace if the Kubernetes object count and policy model remain simple; namespace-per-trip is useful only if it materially improves security or lifecycle isolation. This is an implementation choice, not a product contract.

4. Public routing: one dedicated tunnel, wildcard hostnames for trips

Trips are not assigned individual subdomains and are not path-routed under one origin. A dedicated, in-cluster Cloudflare tunnel (its own named tunnel, run as a Deployment in kinerary-system, never the RPi4's shared config.yml) terminates on one proxied wildcard DNS record. Traefik routes by Host() to the correct trip Service. Path routing was the original proposal here; it was dropped because the trip runtime keeps its session token in localStorage, which is origin-scoped, not path-scoped — two trips sharing one origin would silently share sessions and permissions. A wildcard on the same second-level domain keeps Cloudflare Universal SSL coverage without per-trip certificates.

https://kinerary.example/                    → web portal
https://kinerary.example/api/...             → control-plane API
https://japan.trips.kinerary.example/        → Japan trip runtime
https://italy.trips.kinerary.example/        → Italy trip runtime

Dedicated Kinerary Cloudflare tunnel (own credentials, not the RPi4's)
       │      DNS: kinerary.example → tunnel
       │           *.trips.kinerary.example → same tunnel (wildcard)
       ▼
    Traefik
       │
       ├── Host(`kinerary.example`) && PathPrefix(`/api`)  → control-plane-api
       ├── Host(`kinerary.example`)                        → web portal
       ├── Host(`japan.trips.kinerary.example`)             → trip-japan service
       └── Host(`italy.trips.kinerary.example`)             → trip-italy service
             (unmatched Host → 404, never a default backend)

Creating a trip therefore requires only internal Kubernetes objects: a Deployment/Service and one Traefik Host() rule, both covered by the existing wildcard DNS record and certificate. The control-plane worker does not create a Cloudflare tunnel, DNS record, public IP, or Nginx Proxy Manager host for every family, and it never touches the RPi4. The public edge remains constant.

Required application work: a 2026-09-04 audit found the legacy trip site/server already origin-shaped — no cookies, no server-side redirects, no service worker, no client-side router, and its Telegram/Google login flows are callback-free. The remaining gap is small: enable trust proxy, derive PUBLIC_ORIGIN per trip from its assigned hostname, and stop deriving the site URL from a Proxmox-shaped topology.yaml. No base-path rewrite of the ~100 absolute-path references in site/app.js is needed under this routing model; that work only becomes relevant if path routing is revisited later alongside the newer trip-web front-end.

5. Hermes integration

Kinerary gets a dedicated in-cluster Hermes runtime, built as its own image, once Sprint 6.5 has merged to main — that sprint carries the relay that lets one gateway safely own the shared Telegram bot. Documented fallback: if the Proxmox host cannot spare the resources after its preparation pass, Hermes keeps running on the Mac against the in-cluster relay and APIs over the LAN; that is a recorded deviation from “the Mac is optional,” not a silent compromise, and is revisited at each deployment sprint boundary. The elulhome smart-home profile is out of scope entirely and never receives cluster credentials.

Telegram / Web request
        │
        ▼
Kinerary routing / MCP contract
        │
        ▼
Hermes Service (ClusterIP only)
        │
        ├── interviewer profile
        ├── trip companion profile
        └── extraction/enrichment profile
        │
        ▼
Kinerary APIs / approved tools / external LLM APIs

Hermes is a first-class Kinerary service and is deployed in the same k3s cluster, but not as a sidecar of the API and not with Kubernetes administrator credentials. Kinerary owns tenant identity, approval, routing, and infrastructure mutation. Hermes consumes constrained application/MCP capabilities.

Start with one Hermes runtime and multiple profiles unless runtime isolation requirements force one process per profile. A single replica is appropriate until Hermes state semantics and concurrent profile ownership are explicitly proven safe for horizontal replication.

6. Storage model

DataPrimary storageReason
Kinerary control-plane PostgreSQLlocal SSD PVCtransactional DB; keep latency and filesystem semantics predictable
Trip SQLite / mutable runtime DBlocal SSD PVCsame reason; avoid SQLite over NFS
Hermes runtime/workspace statelocal SSD PVCfast, reliable local state; backed up separately

Container imagesGHCR / registryimmutable deployment artifact, not local state

TrueNAS NFS for documents

Use a dedicated TrueNAS dataset, for example kinerary-documents, exported by NFS and consumed through a Kubernetes PersistentVolume/PersistentVolumeClaim. Store objects under opaque tenant-aware keys rather than filesystem paths derived directly from user input.

TrueNAS dataset: kinerary-documents
  /trips/<trip-id>/booking-confirmations/...
  /trips/<trip-id>/uploads/...
  /trips/<trip-id>/exports/...

k3s
  └── RWX NFS PVC
       └── document/blob service or trip server mount

Prefer an application storage abstraction over arbitrary Pods writing directly to the shared filesystem. That gives Kinerary one place to enforce tenant boundaries, MIME/size validation, retention, provenance, and future migration to object storage.

Failure behavior: an NFS outage should ideally make attachments temporarily unavailable while core account/control-plane data remains operational. Do not place PostgreSQL's data directory or a live SQLite database on this NFS share.

7. Kubernetes-native provisioning

The current worker's Proxmox/LXC/SSH/NPM/Cloudflare adapter path should be replaced for this environment by a Kubernetes runtime adapter.

Confirmed intake
    ↓
Planner + release selection
    ↓
Approved durable job
    ↓
Control-plane worker
    ↓
Kubernetes adapter
    ├── create/update trip identity & labels
    ├── create Secret / ConfigMap
    ├── create PVC(s)
    ├── create trip Deployment(s)
    ├── create ClusterIP Service
    ├── add/update host-based Ingress route
    └── record readiness / resource evidence

No per-trip:
  ✗ Proxmox LXC
  ✗ public IP
  ✗ DNS record       (covered by the one wildcard record)
  ✗ Cloudflare tunnel (one dedicated tunnel, created once)
  ✗ NPM proxy host

The worker receives a dedicated Kubernetes ServiceAccount with the minimum resource verbs needed for the chosen tenancy model. Hermes never receives this ServiceAccount.

8. Release model

Preserve Kinerary's sealed release concept. Replace “verified source tree copied to a remote runtime” with “verified source revision built into an immutable OCI image”. A promoted release should ultimately identify both the source revision and immutable image digest.

git revision
   ↓
release build + sanitation + compatibility checks
   ↓
OCI image build
   ↓
GHCR digest sha256:...
   ↓
release promoted to available
   ↓
planner chooses release
   ↓
worker deploys exact digest

The deployment must not use :latest as a production contract.

9. Trust boundaries and secrets

  • Only Web, trip paths, and specifically required callbacks are public.
  • PostgreSQL, worker, Hermes gateway, privileged MCP surfaces, and internal service APIs remain ClusterIP/private.
  • Continue using file-backed secret references such as file:///run/secrets/...; Kubernetes Secret volumes map naturally to the current contract.
  • Use SOPS/age or another encrypted-at-rest Git workflow if encrypted secret manifests are committed later. Vault is deferred until dynamic secret management provides clear value.
  • Add default-deny NetworkPolicies, then allow only required service-to-service flows.
  • Investigate and remove the legacy trip server's privileged: true requirement before Kubernetes production deployment. Do not translate it blindly into a privileged Pod.

10. Backup and restore

Application data

  • scheduled pg_dump to TrueNAS
  • SQLite-consistent trip backups
  • Hermes state backup with restic/kopia or equivalent
  • NFS document dataset snapshots on TrueNAS
  • Google Drive copy of PostgreSQL/SQLite/Hermes-state backups (off-host)

Platform recovery

  • Proxmox VM backup to TrueNAS
  • k3s datastore + server token backup
  • deployment manifests in Git
  • immutable images in registry
  • periodic restore drill, not backup-only confidence

If TrueNAS is itself a VM on the same Proxmox host, it protects strongly against guest corruption and operator mistakes but not against loss of the physical Proxmox machine. Off-host replication should then be considered separately.

11. Old Mac mini — optional only

The Mac remains on macOS. k3s Linux nodes cannot run natively on macOS, therefore the baseline architecture does not include the Mac as a cluster node and does not depend on it.

Two optional future uses are allowed without changing the production design:

  • External macOS worker: run non-critical build, test, enrichment, or agent tasks outside Kubernetes and invoke them through a constrained queue/API.
  • Linux VM hosted on macOS: only if desired later, a Linux VM could join k3s as an agent. This is optional and does not require replacing macOS.
If neither option is useful, the Mac can simply remain a development/backup Hermes machine. No production requirement depends on it.

12. Deployment and operations

Use Kustomize first, with a repository-owned deployment tree. Do not introduce ArgoCD/Flux as a prerequisite.

deploy/
  base/
    web/
    control-plane-api/
    control-plane-worker/
    postgres/
    hermes/
    trip-runtime/
    ingress/
  overlays/
    home-prod/

kubectl apply -k deploy/overlays/home-prod

CI remains in GitHub Actions and is extended to build and publish versioned images. Production deployment consumes immutable tags/digests. Lightweight logs, resource metrics, probes, and alerting are introduced after the first end-to-end deployment path works.
