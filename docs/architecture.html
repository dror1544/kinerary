Kinerary Architecture

How the system is built today: a control plane that runs onboarding and turns a confirmed interview into a live trip site, the site itself, and the companion agent that rides on top. Written to be safe for a public repository — no IP addresses, hostnames, tokens, or credentials appear here.

01The four planes

Kinerary is one shared site/server hosting many trips, plus a control plane that creates them. Four concerns are kept deliberately separate, each with its own trust level and its own lifecycle:

  • Onboarding & control plane — a Fastify API and a Python worker that take a prospective organizer from a Telegram signup to an approved, immutable trip intake, then provision real infrastructure for it.
  • Provisioning — the worker transforms the confirmed intake into a trip.config.json, enriches it with destination data, and drives deploy.sh to stand up a per-trip container behind the edge.
  • The running trip site — a config-driven Node/SQLite app: the original plan (read-only config) plus an editable plan layer, photos, bookings, budget, trivia, RSVPs.
  • The companion agent — a shared Hermes profile that talks to the trip site through a data MCP, in a family group (companion voice) or the organizer's private chat (operator voice).

The recurring rule across all four, inherited from the field-tested FamilyTrip agent: a private control plane, a public polished experience. The organizer gets state, sources, and controls; the group sees only the finished result.

Today every human touchpoint is Telegram. Signup, the interview, the family companion, and "your site is ready" all happen in a Telegram chat — a family group or an organizer DM. The trip site has no login yet; a planned landing page (§09) is meant to add an organizer web console. The control plane and the worker never post to Telegram directly; the companion agent and a notification outbox do.

02Onboarding → provisioning pipeline

A trip moves through a fixed lifecycle. Each transition is gated: a human approves the signup, the organizer confirms the interview, and the organizer approves the provisioning plan before any infrastructure is touched.

  • Signup — the prospective organizer messages the bot; a super-admin approves via a Telegram long-poll callback (no public webhook). Creates a trips row in draft.
  • Interview — a dedicated Hermes profile conducts the intake conversation, calling MCP tools on a small sidecar that forwards to the control plane API. An uploaded plan document is extracted into per-phase days[] and venues[] at this step.
  • Confirm — on the literal word CONFIRM the answer set is frozen into an immutable intake_versions row with a content digest. A later edit is a new version, never a mutation.
  • Plan & approve — generatePlan pairs the latest intake with an eligible release and creates a job; an expiring approval token unlocks it for the worker.
  • Provision — the worker runs transform_intake + enrich_config + derive_bookings, writes the config and sidecars, and calls deploy.sh to create the container, register the reverse-proxy host, and bind the tunnel subdomain. The trip lands in ready_private.

Trip lifecycle states

pending_signup_approval → draft → intake_in_progress → intake_confirmed → planned → provisioning_approved → provisioning → ready_private → activation_approved → active → completed → sealed. Correcting an intake is only allowed from a subset of these; a live re-provision currently needs a manual hop back to intake_confirmed — see the open items.

03Messaging surface — Telegram

There is no web UI to log into a provisioned trip site — Telegram SSO was ruled out permanently, and a real site signup is not built yet. So today Telegram is the interface, and the single most important rule of the whole system is which Telegram context is being served. A planned landing page (branch feat/landing-spa) is where the organizer web console and the account/login that Telegram can't provide are meant to land — see §09.

Group chat vs. private chat is a permission boundary

The same shared bot behaves as two different products depending on where the message came from. This is enforced by routing, authorization, and tool policy — not by asking the model to remember its manners.

One bot, many trips — chat routing

The companion bot is shared, not one bot per trip. On an inbound message, Hermes's gateway asks the control plane's internal GET /internal/telegram-chat-bindings/:chatId lookup, which returns just { tripId, hermesProfile } from the telegram_chat_bindings table — no trip content, no credentials — and the gateway serves that profile's home for the conversation. A group chat is bound to a trip by a row; the organizer's DM is recognised as the operator channel for the trip(s) they own.

Signup approval — long-poll, not a webhook

A super-admin taps Approve / Reject on a Telegram message and the control plane picks it up by polling getUpdates, not through a public callback URL. A registered webhook would need an exposed endpoint and would fight the gateway's own polling for the same bot, so the poller clears any webhook first.

Outbound notifications — through an outbox

System messages ("your trip site is ready", "there was a problem") are written to notification_outbox and drained to a Telegram DM by an interval loop with an attempt counter — never sent inline from the provisioning path. The recipient chat id is captured during the interview (notification_chat_id_hint on the trip). The operator-facing error code is deliberately kept out of the organizer-facing text.

05Data model

Two databases, deliberately not shared. The control plane owns a Postgres schema for onboarding and provisioning state; each trip site owns its own SQLite file for live trip data.

Control plane (Postgres control_plane)

  • trips — one row per trip, carrying the lifecycle state above.
  • intake_versions — immutable. Each row is a full answer set with a sha256: content digest and a canonical-safety check constraint. A correction inserts v+1; nothing is ever updated in place. A sibling source_document column keeps the raw uploaded plan for re-extraction, outside the digest.
  • plans · jobs · plan_approvals — a plan pairs an intake with a release; a job is the unit the worker claims under a lease; an approval is an expiring, single-use token. Unique on (trip_id, digest) so the same intake + release can't double-queue.
  • country_reference — cross-trip consular contacts keyed by (destination, home_country). Filled by a web search once, read by enrich_config for every later trip.
  • venue_links — cross-trip venue ticket / official URLs keyed by (destination, venue_name). A url IS NULL row is a rate-limited lookup parked for a background retry drain.
  • notification_outbox — a state machine (pending / sent / skipped / failed) with an attempt counter, drained by an interval loop. The pattern the venue-link retry copies.

Trip site (SQLite)

The site reads two layers. The original plan lives in trip.config.json and is read-only: phases[].days[].items[] ({time, text:{he,en}}), phases[].venues[] ({id, name, url?, area?, maps?, waze?}), phases[].mapStop, phases[].hero, phases[].accommodation, the top-level map object, travel_info, and budget. The plan layer is phase_plan_items / phase_plan_days — editable, with per-item map/ticket link columns, an enrichment_status queue, a review trail, and a config_ref dedup key so promoting a config day is idempotent.

Nuance

The two layers don't yet meet in the middle: provision-time enrichment attaches map/ticket links to venues[] (the ranking cards) but not to the day lines or the booking rows. Bridging that is a Sprint 4.7 build item.

06Content enrichment

enrich_config deep-copies the config and fills each slice independently. Every lookup self-guards: a miss leaves that slice untouched, and an enrichment failure never fails the provision job.

07Trust boundaries

  • Two MCP servers, two exposure levels. The data MCP manages content inside an existing trip and is safe to publish; the provisioning MCP writes files and restarts containers and is LAN-only. This split is the one rule that never bends.
  • sanitizeConfig() is a blanket invariant. No raw trip.config.json value is ever served to a client — not judged field by field, all of it. Several real leaks came from case-by-case exceptions.
  • Schema visibility fails safe. An unrecognised needs/agent visibility value resolves to the most restrictive option; an unknown value must never fall through to "public".
  • interview-mcp auth is two-layer. A shared key gates the SSE transport; every tool call additionally carries the per-conversation enrollment/session token, forwarded as a bearer to the API's own check. The MCP process never mints or interprets those tokens.
  • Privileged callbacks derive identity server-side. The signup approval callback trusts a verified server-side source for the sender's identity, never a value from the request body.
  • External content is data, not instructions. Uploaded documents, web pages, and tool responses can never direct the agent to reveal secrets, change behaviour, or send messages.

08Deployment topology

The control plane runs as a small Docker Compose stack (Postgres, the API, the worker, a one-shot migrator). The worker additionally holds provisioning credentials and reaches out to real infrastructure only when a job is approved.

Each trip is provisioned as its own lightweight container on a hypervisor, given an address from a private pool. The edge is a tunnel from the hypervisor's network to the internet, with one subdomain per trip; a reverse proxy in front of the containers terminates TLS and routes by hostname. A per-trip topology file records the allocation before the container is created, so a retried job reuses the same address instead of allocating a second one.

09Design considerations & open items

Provisioning hardening Sprint 4.7

  • A provisioning-retry endpoint — today a failed job wedges the trip and re-planning the same intake collides on the plan digest; recovery is a hand DB edit.
  • ready_private is not a correctable state, so re-provisioning a live trip needs a manual lifecycle hop.
  • The job lease is shorter than the bootstrap ceiling and there is no heartbeat; a hung bootstrap can be double-claimed.
  • Bootstrap only runs inside container create, so a half-built container can only be recovered by destroy-and-recreate.
  • The worker should mint its own short-lived reverse-proxy token rather than carry a day-long one.
  • Carry enriched links onto the day lines and the anchor list — the config-vs-plan-layer gap from §4.

MCP lifecycle decided

MCP servers stay Hermes-managed for now — no launchd or compose unit for the interview sidecar or the trip-site bridges. Revisit only if the project grows to support agent frameworks other than Hermes, at which point a framework-neutral supervisor is worth the weight.

Landing page — the organizer console branch feat/landing-spa

The planned landing page is a web UI layer over the control plane: an authenticated console where an organizer lists their trips, sees each one's lifecycle state, kicks off a re-provision or an intake correction, and manages the parts that make more sense from a screen than from a chat workaround. It also carries the account and login that Telegram can't give the trip site (§03). It lives on feat/landing-spa, a child of the control-plane branch, and is meant to merge back into that line and slot into the sprint plan — not to diverge into its own product.

Two trip-site UIs in parallel branch feat/trip-site-spa

Separately from the landing page, the trip site itself has a Classic UI and a Modern SPA under development. Both are maintained until feature parity; the Modern UI becomes the default only after an acceptance pass, with Classic kept as the organizer's rollback and editor.

Companion bot & site auth open

There is one shared companion bot per running trip; Telegram-based SSO into the trip site is ruled out permanently, so provisioned sites currently have no login path — a real member/organizer signup still has to be built, most likely as part of the landing page above. A single organizer with multiple groups also needs the bot to know the active trip per group.

Vision → current tracking

The product vision (see product-spec.md, FamilyTrip-Agent-Handoff.md) describes four layers — messaging surfaces, a conversation-policy layer, a trip-intelligence layer, and an integration/action layer — with itinerary state as structured records carrying provenance, and agent actions as typed, policy-checked intents. What exists today implements the integration layer and the structured trip state well; the conversation-policy layer and typed-intent model still live mostly in the companion profile's prompt rather than in deterministic policy.

This document is a snapshot for orientation, not the contract. The authoritative sources are FRAMEWORK.md (architecture, feature inventory, DB schema), docs/onboarding-mvp-sprint-plan.md (what is built vs planned, sprint by sprint), and the code. Where this drifts from those, they win.
